# Agent Note：为每次全新 TUI 启动分配唯一会话

Status: implemented

[English](2026-08-14-tui-fresh-session-identity.md) | 中文

## 问题

随附的 TUI runner 会用固定会话 id `main` 创建每一个未恢复进程。当一个进程已经持久化该 id 后，后续进程会用同一 id 创建另一个内存会话；持久化层会正确地把首次追加拒绝为身份冲突。因此，全屏界面可能看起来已经就绪，但对话本身无法使用。删除旧日志会丢失历史，而静默恢复它又会让全新启动接入陈旧状态，并保留跨进程所有权歧义。

## 决策

未恢复的 runner 启动现在会在调用 `agents.create()` 前分配 `session-<UUID>`。新建对话的交换流程复用同一分配器。只有显式提供 `resumeSessionId` 时才调用 `agents.resume()`，因此已有的 `main` 日志保持不变，仍可通过 `dsh tui --resume main` 进入。

身份分配不执行持久化预检。随机 UUID 避免了先检查后创建的竞态；如果 runner 通过搜索空闲的可读计数器来命名，该竞态仍会存在。

## 考虑过的替代方案

**在 `main` 存在时自动恢复。** 这会让普通的全新启动静默继承旧对话状态，而且仍可能让两个进程争用同一个持久写入方。

**探测存储并分配可读计数器。** 除非持久化层同时提供原子预留协议，否则先检查后创建仍存在跨进程竞态。UUID 分配不需要预检，也不需要新的存储契约。

**删除或重命名旧 `main` 日志。** 修改用户历史没有必要，还会让修复带有破坏性。显式恢复可让该历史继续以原 id 使用。

## 验证

runner 单测断言两次独立的未恢复启动会获得不同的持久身份。基于构建产物的 keyless PTY 测试使用同一 `DSH_HOME` 和工作区启动 CLI 两次，确认两次启动都不报告 id 冲突，并验证产生了两份不同的持久会话日志。

## 后果

普通的重复启动不再争用共享 `main` 日志，也不会重命名或删除任何已有历史。全新会话 id 会有意采用不易记忆的形式；退出消息、`/status`、`/resume` 和会话选择器会显示可恢复的精确 id。多个进程显式恢复同一 id 时，仍需在 TUI 外协调所有权。
